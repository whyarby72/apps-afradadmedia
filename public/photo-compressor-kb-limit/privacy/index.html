1. Scope

This Privacy Policy describes how Photo Compressor: KB Limit handles information when you use the Android app. The app's core purpose is to help you reduce a JPEG/JPG toward a file-size limit that you provide, verify the resulting size, and save or share a copy.

This policy distinguishes the app's local photo-processing behavior from data that may be processed by Google advertising and consent services in an ad-enabled release.

2. Photos you choose

When you choose a JPEG/JPG, the app may read information needed to perform the compression job, including the file's display name, MIME type, byte size, image dimensions and EXIF orientation when available.

The selected photo is processed locally on your device for the core compression workflow. The app's core compression code does not upload the selected source JPEG to an Afradad Media server for compression.

The app code is not designed to intentionally send your source JPEG bytes or the KB/MB target you enter to Google Mobile Ads.

3. Compression and result files

JPEG recompression and resizing are performed on-device. For a known target, the app checks the actual result bytes against the limit you selected. If you use the unknown-limit path, the app may create a smaller copy but does not claim that the result will meet a specific website or form requirement.

Temporary result

A generated result is temporarily stored in the app's cache so it can be previewed, saved or shared. The app reuses its result cache as new outputs are produced, and Android may clear app cache as part of normal system storage management.

Saved copy

Saving is an explicit action. When you choose Save, the app writes a separate JPEG copy to the device's media storage, under the Pictures area used by the app. Saved copies remain under your device/storage management until you delete or otherwise remove them.

Share

Sharing is also an explicit action. The app provides the result through a read-only Android content URI to the app or service you choose. After you share a file, the receiving service's own privacy practices apply.

Original photo

The normal compression workflow does not overwrite the source photo.

4. Image metadata

When the app recompresses an image, the new JPEG is produced from decoded image pixels. Metadata from the source is not preserved in the same way as the original file. The app also uses EXIF orientation information, when available, to avoid silent orientation errors during processing.

If a source image already meets the requested limit and does not need recompression, the app may copy that source instead. For that reason, metadata behavior can differ between a recompressed result and a copied already-ready result.

5. Accounts and developer cloud storage

No user account or login is required for the core compression workflow. Afradad Media does not require a developer-owned cloud photo store or backend server to perform the core compression job.

6. Advertising and Google consent services

An ad-enabled release of the app may use the Google Mobile Ads SDK (AdMob) to display advertising and Google's User Messaging Platform (UMP) to request or manage consent choices where required.

Google advertising and consent services can process data that is separate from the JPEG content handled by the local compression workflow. Depending on Google's current SDK behavior, configuration, consent state and applicable law, this can include device, network, advertising, interaction, diagnostic or fraud-prevention related information.

The current product architecture does not use Firebase Analytics, custom analytics or ad mediation. The current test architecture also disables Google's publisher first-party ID feature before ads become eligible.

Advertising or consent failures are not intended to block the core photo-compression workflow.

7. Consent and privacy choices

The app's current monetization/privacy architecture uses Google's UMP consent information as a gate before ad requests are permitted. Where Google reports that privacy options are required, the app is designed to expose a Privacy choices entry point.

The exact consent experience can vary by region, applicable rules, Google configuration and the release artifact in use.

8. Analytics

The current product candidate does not use Firebase Analytics or a custom analytics service. If this changes in a later release, this policy and the relevant store disclosures must be updated before that behavior is represented as current.

9. Permissions and system access

The app uses Android system photo/document and media APIs to let you choose, save and share files. The final permissions and SDK-contributed manifest entries for an ad-enabled release must be determined from the merged manifest of that exact release artifact.

This policy therefore does not make a fixed, exhaustive permissions claim based only on the app's handwritten AndroidManifest.xml.

10. Security

The core compression job is designed to operate locally on the device, reducing the need to transmit your selected photo to an Afradad Media server for processing. No method of software operation or data transmission can be described as perfectly secure, and third-party services used by an ad-enabled release are governed by their own security practices.
